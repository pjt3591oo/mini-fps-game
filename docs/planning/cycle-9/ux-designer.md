# 사이클 9 기획안 — UX 기획자

읽은 것: `docs/PLAN.md`(사이클 1~8), 지난 기획안, `public/index.html`, `public/js/shop.js`, `hud.js`, `perks.js`, `main.js`(훅·잠금·입력·`step`), `enemies.js`(`updateWaves`, `addStrike`, `callStrike`), `config.js`(`ITEMS`·`SUPPLIES`·`UPGRADE`).
코드는 고치지 않았고 플레이테스트 도구도 실행하지 않았다. `docs/screenshots/` 3장은 사이클 8 이전 화면이라(상단에 크레딧 칸 없음, 아이템 줄 없음) 상점·아이템 배치는 CSS 수치로 계산했다. 브라우저에서만 확인되는 항목은 **[실기 확인 필요]**로 표시했다.

우선순위는 **안 1 > 안 2 > 안 3**. 안 1의 2번은 웨이브 시작 조건을 건드리므로 시스템 기획자 확인이 필요하다(UX 요구만 적고 값은 넘긴다).

## 안 1. 웨이브 사이: 특성을 고르면 상점이 닫히는 순서 문제와 세 번 겹치는 안내

### 문제와 근거

마지막 적을 잡은 프레임에 뜨는 것(720p 기준 위에서 아래로): `#banner` "WAVE n 클리어 / 크레딧 +N · 체력 +25 · B 상점"(180px, 2.6초) → `#perkhint`(약 350px) → `#perks` 카드(380~540px) → `#perkbar`(556px) → `#hint`(578~616px, 카드가 닫힌 뒤에만) → `#inter` "B 상점 / Enter 다음 웨이브"(624~656px). 서로 겹치지는 않는다. 문제는 순서와 내용이다.

| 문제 | 근거 |
| --- | --- |
| **솔로에서 특성을 먼저 고르면 상점을 열 시간이 없다.** 클리어 3초 뒤에 고르면 그 프레임에 다음 웨이브가 시작된다. 3초 안에 골라도 상점 창구는 3초 시점에 닫힌다. 카드가 화면 한가운데 있으니 "특성 → 상점"이 자연스러운 순서인데, 실제로 되는 순서는 "상점 → 특성"뿐이다 | `enemies.js` `updateWaves()`: `waves.timer < 7 && perkDone() && !net.connected`이면 `startWave`. 사이클 7까지는 장점이던 규칙이 상점과 충돌한다 |
| 상점을 닫는 순간에도 같은 일이 난다. 특성을 이미 골랐고 타이머가 7 아래면 닫은 다음 프레임에 웨이브가 시작된다. 마우스 잠금을 다시 잡는 도중이다 | 같은 조건. `shopFreezesTimer()`는 상점이 열린 동안만 막는다 |
| 첫 상점 힌트가 쓸 수 없는 순간에 뜬다. 힌트는 카드가 닫힌 뒤에만 나오는데, 솔로에서 그때는 웨이브가 막 시작됐거나 곧 시작된다. B를 누르면 "상점은 웨이브 사이에만 열 수 있습니다"가 돌아온다 | `main.js` `G.hooks.waveClear`의 `hint('shop', …)`, `updateHints()`의 `perkOpen()` 반환, `keydown`의 KeyB 분기 |
| `#inter`가 듣지 않는 키를 안내한다. 카드가 열린 동안 Enter는 무시되고, 협동 참가자의 Enter는 언제나 아무 일도 하지 않는다 | `index.html` `#inter`는 고정 문구. `keydown`의 `e.code === 'Enter' && !perkOpen()`, `updateWaves()` 첫 줄의 호스트 검사 |
| "B 상점"이 한 화면에 세 번 나온다 | 배너 부제, `#inter`, `hint('shop')` |
| 카드가 뜬 채 상점을 열면 카드·막대가 72% 어둠 뒤에 남는다(가운데 880px는 상점 상자에 가려짐). 상점 안에서는 특성이 남았다는 것도, 남은 시간도 알 수 없다 | `#shop`은 `z-index:5`, `rgba(5,8,13,.72)`. `openShop()`은 `#perks`를 건드리지 않는다. 상점 중 키는 B·Esc·Enter만 받는다 |
| 협동은 상점 중에도 20초가 흐른다. 시간이 다 되면 상점 뒤에서 무작위 특성이 지급되고 상점이 예고 없이 닫힌다 | `waves.timer = 20`, `shopFreezesTimer()`는 `!net.connected`일 때만 참. `G.hooks.waveStart`의 `closePerks(true)` → `hideShop()` |

정리하면 솔로는 "상점을 열면 멈추지만 열 기회가 사라지고", 협동은 "열 기회는 있지만 안에서 시간이 보이지 않는다".

### 제안

1. **`#inter`를 웨이브 사이의 유일한 안내 줄로 만든다.** 상태별 문구:
   - 카드 열림: `[B] 상점` (Enter 표기 없음)
   - 카드 닫힘, 솔로·호스트: `[B] 상점   [Enter] 다음 웨이브 · 3초` (숫자는 매초 갱신)
   - 카드 닫힘, 참가자: `[B] 상점   다음 웨이브까지 12초`
   - 상점을 한 번도 연 적 없는 플레이어(저장된 힌트 기록 `shop` 없음)에게는 첫 줄을 `[B] 상점 — 크레딧으로 무기 강화 · 아이템 구매`로 늘리고 테두리를 호박색으로 한다. 상점을 처음 열면 '봤음'으로 저장.
2. **특성을 고른 뒤와 상점을 닫은 뒤에 `#inter`를 읽고 B를 누를 시간을 보장한다.** UX 요구는 "두 시점 모두에서 다음 웨이브까지 최소 3초가 남고, 그 숫자가 `#inter`에 보인다"이다. Enter로 즉시 시작은 그대로 둔다. 구체 값과 구현 방식은 시스템 기획자 판단.
3. **뺄 것.** 배너 부제에서 `· B 상점` 삭제(`크레딧 +N · 체력 +25`만). `hint('shop')` 삭제(1번의 첫 회 문구가 대신한다).
4. **상점이 열린 동안 `#perks`·`#perkbar`·`#perkhint`를 숨기고**, 상점 머리줄 제목 옆에 한 줄을 둔다.
   - 솔로, 특성 미선택: `특성 선택이 남아 있습니다 — 상점을 닫으면 이어집니다`
   - 협동: 폭 220px 남은 시간 막대 + `다음 웨이브까지 12초` (특성 미선택이면 뒤에 ` · 특성을 고르지 않으면 무작위 지급`). 5초 이하에서는 굵은 글씨와 `곧 닫힙니다`를 붙여 색에만 기대지 않는다.
5. 협동에서 상점이 강제로 닫히면 킬 피드에 `웨이브 시작 — 상점이 닫혔습니다` 한 줄.

### 기대 효과
첫 판 플레이어가 "특성 고르고 → 상점 들르고 → 시작"을 헤매지 않고 한다. 웨이브 사이에 읽을 글이 배너·힌트·안내 줄 세 곳에서 안내 줄 한 곳으로 준다. 협동에서 구매 도중 화면이 사라지는 일이 예고된다.

### 구현 비용: 낮음~중간
`index.html`(`#inter`, `.shophead`), `hud.js`(`setInter`에 문구 인자), `main.js`(`G.hooks.waveClear`, `step`의 `setInter` 호출, `G.hooks.waveStart`), `shop.js`(`openShop`/`closeShop`에서 카드 숨김, 머리줄 갱신), `perks.js`(숨김·복귀), 2번은 `enemies.js`(`updateWaves`).

### 위험과 완화책
- 2번으로 솔로 웨이브 간격이 최대 3초 늘 수 있다 → Enter 즉시 시작을 `#inter`에 항상 표기해 숙련자는 손해가 없다.
- 참가자는 호스트의 `waves.timer`를 모른다 → `clear` 메시지의 `info.t`에서 자체로 세고(지금 `#perkbar`가 쓰는 방식), 어긋나도 되도록 5초 이하 경고는 막대 기준으로만 낸다.
- 봇(`updateBot`)은 화면을 거치지 않고 `tryUpgrade`를 부르므로 표시 변경의 영향이 없다. 2번은 봇 판 길이를 늘릴 수 있어 회귀 기준 시간을 함께 본다.

### 성공 확인 방법
- 시나리오(`?debug`): 1웨이브 클리어 5초 뒤 `choosePerk` → 이후 3초 안에 `canShop()`이 참인지. 상점을 닫은 직후 프레임에 `waves.inter`가 유지되는지.
- 화면: 카드가 뜬 채 `showShop()` 후 720p 캡처에 카드가 보이지 않고 머리줄 문구가 있는지.
- 사람 플레이: `data/runs.jsonl`의 `shopSeen` 비율과 판당 강화·구매 횟수를 전후 비교(지금은 솔로에서 낮게 나올 것으로 예상).

## 안 2. 상점 화면: 보이지 않는 강화 결과와 마우스 잠금 복귀 실패

### 문제와 근거

강화 버튼을 누른 플레이어의 눈은 그 버튼 위에 있다.

| 문제 | 근거 |
| --- | --- |
| 강화 결과 문구가 상점 뒤에 있다. 성공·실패는 킬 피드로만 나가는데 피드는 화면 오른쪽 끝 13px 글씨이고 72% 어둠에 덮인다 | `shop.js` `tryUpgrade()`의 `G.hooks.feed`, `#feed`는 `#hud` 안(right 16px, top 206px), `#shop`이 그 위를 덮는다 |
| 실패하면 상점 안에서 바뀌는 것은 머리줄의 크레딧 숫자와 버튼 안 10.5px `성공 65%` → `75%`뿐이다. 소리는 빈 탄창 소리(`sfx.empty`)다. "안 눌렸다"로 읽고 다시 누르면 최대 420이 또 나간다 | `tryUpgrade()` 실패 분기, `render()`가 버튼을 같은 자리에 다시 그림, 클릭 유예 없음 |
| 비활성 버튼이 이유를 말하지 않는다. 크레딧 부족·최대 보유·체력 가득이 모두 같은 흐린 버튼이다 | `render()`의 `btn(…, ok)`, `.srow button:disabled` |
| 보급을 살지 판단할 현재 상태가 상점 안에 없다. 체력·수류탄·탄약 HUD는 어둠 뒤에 있고 창이 좁으면 상자에 가려진다. 탄약 보급은 가득 차 있어도 팔린다 | `SUPPLIES` 행에는 설명뿐, `buySupply('ammo')`에 가득 참 검사 없음 |
| 상점을 닫을 때 잠금 재획득이 거부되면 설명 없는 "일시정지" 화면으로 넘어가고 버튼은 0.8초 잠긴다. 협동에서는 그동안 세계가 계속 돈다 | `hideShop()` → `controls.lock()`, `pointerlockerror` → `onUnlock()` → `setOverlay('pause')`의 800ms 유예 |
| Esc로 닫는 경로가 특히 의심스럽다. Esc 키 입력은 브라우저가 사용자 동작으로 쳐 주지 않을 수 있다 **[실기 확인 필요]** | `keydown`: 상점 중 `Escape` → `hideShop()` |
| 협동 강제 닫기는 사용자 입력 없이 잠금을 요청한다. 거부되면 적이 나오는 중에 일시정지 화면이 뜬다 **[실기 확인 필요]** | `G.hooks.waveStart` → `hideShop()` |
| 잠금 요청이 성공도 오류도 내지 않으면 복구 수단이 없다. `G.mode`는 `playing`인데 커서는 풀려 있고, 다시 잠그는 코드는 `enterPlay()`뿐이다 **[실기 확인 필요]** | `public/js` 전체에서 `controls.lock()` 호출은 `enterPlay`와 `hideShop` 두 곳 |
| B를 아주 빠르게 두 번 누르면 잠금 해제 이벤트가 상점이 닫힌 뒤에 도착해 일시정지로 넘어갈 수 있다 **[실기 확인 필요]** | `showShop()`의 `controls.unlock()`은 비동기, `onUnlock()`은 `G.shopOpen`만 본다 |

### 제안

1. **결과 줄.** 상점 머리줄 아래에 높이가 고정된 한 줄(`#shopmsg`)을 둔다. 다음 구매 전까지 유지한다.
   - 성공: `성공 — 소총 +4 · 피해 +10%` (+3·+5·+7은 해당 효과 문구)
   - 실패: `실패 — 샷건 +3 유지 · 180 크레딧 소모 · 다음 성공 확률 75%`
   - 구매: `구급 주사 구매 — 보유 2 / 3 · 전투 중 Z로 사용`
   - "성공/실패" 글자를 맨 앞에 두어 색 없이도 읽힌다. 해당 행은 0.6초간 테두리 강조. 실패 소리는 빈 탄창 소리와 다른 것으로(음향 담당 판단).
2. **연타 방지.** 강화를 시도한 버튼은 0.4초간 눌리지 않는다(사이클 7의 `#resume.wait`와 같은 방식).
3. **비활성 이유를 버튼에 적는다.** `크레딧 부족 (-45)` / `최대 보유` / `가득 참`. 가격은 그대로 보인다.
4. **보급 행에 현재 값.** `응급 처치 — 현재 체력 62 / 100`, `수류탄 2개 — 현재 1 / 4`, `탄약 보급 — 예비 탄약 가득 참`(가득일 때만 표시). 가득 찬 탄약 보급을 막을지는 규칙이므로 시스템 기획자에게 넘긴다.
5. **잠금 복귀 실패 처리.**
   - 상점을 닫다 실패해 일시정지로 넘어간 경우 문구를 `마우스를 다시 잡지 못했습니다 — Enter 또는 '계속하기'를 누르세요`로 하고 0.8초 유예를 두지 않는다.
   - 닫고 0.5초 뒤에도 잠금이 없고 `G.mode`가 `playing`이면 같은 화면으로 보낸다(조용한 실패의 출구).
   - 상점을 연 뒤 0.3초 동안은 B를 닫기로 받지 않는다.
   - 협동 강제 닫기에서 실패하면 문구는 `웨이브가 시작됐습니다 — Enter로 복귀`.

### 기대 효과
강화 실패가 "버그"가 아니라 "실패"로 읽히고, 다음 확률이 올랐다는 보상이 전달된다. 잘못된 재클릭으로 크레딧을 잃지 않는다. 잠금 실패가 어떤 경로로 나도 플레이어에게 다음 행동이 한 줄로 주어진다.

### 구현 비용: 낮음
`shop.js`(`render`, 클릭 처리, 결과 문자열), `index.html`(`#shopmsg`, 버튼 상태 스타일), `main.js`(`hideShop`, `pointerlockerror`, `onUnlock`, `showShop`).

### 위험과 완화책
- 결과 줄로 상점 높이가 늘어 720p에서 스크롤이 생길 수 있다 → 줄 높이 22px 고정, 하단 `.note` 문구를 결과 줄과 겹치는 내용만큼 줄인다("실패해도 단계는 내려가지 않고…"는 실패 문구가 대신 말한다).
- 0.5초 감시가 정상적으로 느린 잠금을 실패로 오판할 수 있다 → 오판해도 Enter 한 번으로 돌아오며, 실기에서 잠금 소요 시간을 재고 값을 정한다.
- 디버그 모드는 잠금을 쓰지 않는다 → 5번은 `!G.debug`에서만 동작, 1~4번은 모드와 무관.

### 성공 확인 방법
- 시나리오: `Math.random`을 고정해 실패시킨 뒤 `#shopmsg` 문구에 "실패"와 다음 확률이 있는지. 0.2초 간격 두 번 클릭 시 크레딧이 한 번만 줄었는지.
- **[실기 확인 필요]** Chrome·Firefox·Edge 각각: B / Esc / Enter / 닫기 버튼으로 닫기, 구매 직후와 5초 이상 가만히 있은 뒤 Esc로 닫기, 협동 강제 닫기, B 빠르게 두 번. 각 경우 잠금 복귀 여부와 뜨는 문구를 표로 기록한다.

## 안 3. 전투 중 아이템: 반응 없는 키, 조준할 수 없는 폭격, 읽히지 않는 방어막

### 문제와 근거

체력 20에서 Z를 누르는 플레이어는 조준선과 왼쪽 아래 체력 숫자 사이를 본다.

| 문제 | 근거 |
| --- | --- |

### 제안

1. **조준선 아래 한 줄(행동 결과 줄).** 조준선 아래 40px에 0.9초 표시. 실패 안내를 킬 피드에서 이쪽으로 옮긴다(피드에서는 뺀다).
   - 0개: `구급 주사 없음 — 웨이브 사이 B 상점` + 빈 소리 + 해당 칸 흔들림
   - `체력이 가득 찼습니다` / `폭격 지점 없음 — 땅이나 벽을 조준하세요`
2. **아이템 칸 정리.** 이번 판에 한 번도 산 적 없는 아이템 칸은 숨긴다. 산 뒤에는 0개가 돼도 흐리게 남겨 "다 썼다"를 보여 준다.
3. **구매 시점 소개.** 아이템을 처음 산 뒤 상점을 닫으면 힌트 1회: `Z 구급 주사 · X 방어막 · T 폭격 — 보유 수는 왼쪽 아래에 있습니다`(산 것만 나열). 안 2의 구매 결과 줄 `전투 중 Z로 사용`과 짝을 이룬다.
4. **폭격 미리 보기.** T를 누르고 있는 동안 조준 지점에 반경 7m 점선 원을 보여 주고, 떼면 요청한다. 짧게 누르면 지금과 같다.
   - 내가 원 안이면 원 무늬를 빗금으로 바꾸고 결과 줄에 `폭발 범위 안 — 나도 다칩니다`
   - 누른 채 우클릭하면 취소(`폭격 취소`)
   - 비용이 부담되면 축소안: 미리 보기 없이, 요청 직후 내가 범위 안일 때만 `폭발 범위 안! 2초 안에 벗어나세요`를 결과 줄에 띄운다.
5. **방어막 표시.** 켜진 동안 화면 테두리에 가는 하늘색 선(색각 보완으로 네 모서리 꺾쇠 모양), 문구는 `방어막 · 피해 -70% — 4초`. 남은 1.5초부터 깜박임과 종료음. 보급품 배너 제목은 `보호막` → `추가 체력`으로 바꿔 이름 충돌을 없앤다.

### 기대 효과
아이템 키가 "눌러도 되는지 모르는 키"에서 결과가 즉시 돌아오는 키가 된다. 140크레딧짜리 폭격을 자기 발밑이나 벽 위에 낭비하지 않는다. 방어막이 켜진 6초를 알고 전진할 수 있다. 첫 웨이브 HUD에서 칸 세 개가 빠진다.

### 구현 비용: 중간 (1·2·3·5는 낮음, 4만 중간)
`shop.js`(`useItem` 분리: 조준·확정), `main.js`(`keydown`/`keyup`의 T, 힌트, 훅), `hud.js`(결과 줄, `el.items`, `el.buff`), `index.html`(결과 줄·테두리 요소), `enemies.js`(미리 보기 원: `addStrike`의 지오메트리 재사용).

### 위험과 완화책
- 결과 줄이 `#prompt`(부활 안내, 60%)·`#hint`와 겹칠 수 있다 → 조준선 바로 아래(약 55%)에 한 줄만, 부활 안내가 떠 있으면 결과 줄을 내지 않는다.
- T 누르고 있기가 숨은 조작이 된다 → 폭격 구매 결과 줄에 `T를 누르고 있으면 지점 미리 보기`를 넣는다.
- 테두리 선이 피격 붉은 테두리(`#hurt`)와 섞인다 → 선은 가장자리 3px 안쪽에만, `#hurt`는 넓은 번짐이라 모양으로 갈린다. 720p 캡처로 확인.
- 봇은 `useItem('medkit')`을 직접 부른다 → 즉시 사용 경로를 그대로 남겨 회귀 테스트가 변하지 않게 한다.

### 성공 확인 방법
- 시나리오: 보유 0에서 KeyZ → 결과 줄 문구 존재, `G.used.medkit` 변화 없음. 보유 1, 발밑 조준 T 유지 → 경고 문구, 우클릭 → `G.inv.strike` 그대로.
- 화면: 방어막 켠 상태와 피격 상태를 각각 캡처해 흑백 변환 후 구분되는지.
- 사람 플레이: `runs.jsonl`의 `used`(종류별 사용 수)와 사망 원인 "아군 폭격" 비율을 전후 비교.

- 상점 가격·확률·보유 한도는 밸런스 기획자 담당이라 다루지 않았다.
